# 0079. Session-key provisioning custom resource and rotation; scoped exception to 0068

Status: Accepted (M10)

## Context

The session key (0078) must be in two places: the KeyValueStore, where the edge function verifies cookies, and a Secrets Manager secret, where the viewing Lambda signs them. No key may appear in a template or an asset, the agent never writes or rotates secrets, and a failure must keep viewing closed.

- `AWS::CloudFront::KeyValueStore` can only seed a new store from `ImportSource`, which cannot be updated and would put the key into the template or an S3 asset ([AWS::CloudFront::KeyValueStore](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-cloudfront-keyvaluestore.html)). Writes after creation go through the KeyValueStore data-plane API with the store's `ETag` as `IfMatch`; that API is global and signed with SigV4A ([Work with key value data](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/kvs-with-functions-kvp.html)). `@aws-sdk/client-cloudfront-keyvaluestore` throws unless `@aws-sdk/signature-v4a` (or the CRT signer) is installed and imported explicitly, and AWS does not document either in the Lambda runtime (F2). The owner chose a construct custom resource whose bundle carries both packages, as root devDependencies only (Q1 A).
- A new store starts `PROVISIONING` and later becomes `READY` (or fails the import); `DescribeKeyValueStore` returns `Status` and `ETag` and may throw `ConflictException` ([Create a key value store](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/kvs-with-functions-create.html); [DescribeKeyValueStore](https://docs.aws.amazon.com/cloudfront/latest/APIReference/API_kvs_DescribeKeyValueStore.html)). AWS does not say whether CloudFormation waits for `READY` (F10).
- Store data reaches the edge "within seconds", with no stated bound ([Connection Function code, KeyValueStore integration](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/write-connection-function-code.html); [launch post](https://aws.amazon.com/blogs/aws/introducing-amazon-cloudfront-keyvaluestore-a-low-latency-datastore-for-cloudfront-functions/)) (F11).
- ADR 0068 keeps every runtime `@aws-sdk/*` package external to the Lambda assets.

## Decision

- **Resource:** a `CustomResource` `SessionKeys` of type `Custom::ArtifactSessionKeys` whose service token is the `SessionKeysFunction` ARN itself — no CDK `Provider` framework, so no framework Lambda — with properties `SecretArn`, `KeyValueStoreArn` and `Rotation` (the `viewing.sessionKeyRotation` label) and a 5-minute service timeout. The function (`nodejs24.x`, arm64, 256 MB, 120 s) has its own log group and role: `secretsmanager:GetSecretValue` and `PutSecretValue` on the session secret, `cloudfront-keyvaluestore:DescribeKeyValueStore`, `ListKeys` and `UpdateKeys` on the store (one atomic `UpdateKeys` replaces `PutKey`/`DeleteKey`; `ListKeys` finds stray keys), and log writes. The secret is created with the placeholder `{"version":1,"current":null,"keys":{}}` and pinned; the store is created empty. The distribution depends on the custom resource. (The construct resources land with the distribution; this ADR lands with the handler and the bundle.)
- **Ensure** (`ensureSessionKeys`, Create and Update), with injected ports and clock:
  1. Read the secret: a key set or the placeholder; anything else **fails** — the secret is never overwritten blindly.
  2. **Label-selective:** if a key carries the label, it becomes current and the other key previous; otherwise a new `kid` (8 random bytes, hex) and key (32 random bytes, base64url) with that label become current and the old current becomes previous. Everything else is dropped, so the set never holds more than two keys.
  3. **Wait for `READY`:** `DescribeKeyValueStore` every 2 s; `ConflictException` and `ResourceNotFoundException` count as not ready yet (the data plane may not see a store the control plane just created); a status containing `FAIL` (the docs say `IMPORT_FAILED`, the SDK's example `IMPORT_FAILURE`), another error or 60 s fail.
  4. **KVS first:** `ListKeys` (all pages), then one `UpdateKeys` with the `ETag`, putting the set and deleting every other key; skipped when the store already equals the set. An ETag conflict (`ConflictException` or HTTP 412) re-describes and retries, three attempts in all.
  5. **15 s propagation wait** when the current `kid` changes (first create, rotation, rollback), so the edge has had time to see a `kid` before any Lambda signs with it.
  6. **Then the secret**, only if the set changed.
  7. SUCCESS with `PhysicalResourceId` `session-keys` (Create) or the event's own (Update), `NoEcho: true` and `Data: {CurrentKid}`.
- **Rollback safety:** a CloudFormation rollback re-sends the old label, which makes the old key current again instead of rotating a second time and logging everyone out; repeated Updates are no-ops, and manual drift in the store heals.
- **Delete** answers SUCCESS and touches nothing: the secret and the store have their own lifecycle, and a replaced custom resource must not erase keys its successor has just ensured.
- **Fail closed:** every failure answers FAILED with `Reason` = `<error name>: <fixed message>` (at most 256 characters; the SDK error's name only, never its message, and never key material), so the deployment fails and rolls back. An event without an https `ResponseURL` is logged and thrown. The response is a `PUT` to the presigned URL with an empty `content-type`, the event's `StackId`, `RequestId` and `LogicalResourceId`, and a 10 s timeout; a network error, timeout or non-2xx status logs `artifact session-keys response failed {"status":n}` and throws, and CloudFormation fails the resource at the service timeout.
- **The viewing Lambda's key cache** (`createKeyCache`): 5 minutes, single-flight, failures not cached; an unknown `kid` on a login-transaction cookie forces one reload, at most once per 60 seconds, so a rotation does not break sign-ins in flight (0081).
- **Scoped exception to 0068:** `dist/assets/session-keys/index.mjs` bundles `@aws-sdk/client-cloudfront-keyvaluestore` 3.1152.0 and `@aws-sdk/signature-v4a` 3.1138.0 (imported explicitly), both pinned root devDependencies, with their `@aws-sdk/*` and `@smithy/*` dependencies; `@aws-sdk/client-secrets-manager` stays external. `pnpm bundle` fails if this bundle contains an `@aws-sdk` package outside the allowlist (`client-cloudfront-keyvaluestore`, `signature-v4a`, `signature-v4-multi-region`, `core`, `types`, `nested-clients`, `token-providers`, `region-config-resolver`, `xml-builder`, `middleware-*`, `util-*`, `credential-provider-*`), lacks the KVS client or the signer, or loses the external Secrets Manager import; a new package after an SDK bump is reviewed before the list grows. Every other bundle keeps all of `@aws-sdk/*` external. Runtime `dependencies` stay the v1 four and the optional peers the three of 0073.
- **Rotation (owner):** set `viewing: { sessionKeyRotation: "<new label>" }` in the stage, commit, deploy `prod/Platform`, then run `pnpm smoke --view-only`: S38 checks that cookies signed with the previous and the current `kid` are accepted, S41 that new cookies are signed with the new `kid`. Cookies signed with the old key keep working until the next rotation, so rotating twice logs everyone out. The agent never changes the label.

## Consequences

Keys are generated at deploy time and exist only in the secret and the store; nothing manual is needed on the first deploy. The session-keys bundle is about 0.8 MB, against about 0.1 MB for the viewing bundle, and an SDK bump can fail the build until the allowlist is reviewed. A POP that takes longer than 15 s to see a rotated key causes at most a brief login loop, never wider access. A failed provisioning fails the whole deploy rather than opening an edge without keys.
