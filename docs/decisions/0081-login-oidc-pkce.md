# 0081. Login: OIDC code + PKCE, transaction cookie and login cache behaviour

Status: Accepted (M10)

## Context

The viewing plane is behind login from the first deploy, and only the owners may sign in. The plan puts the login routes in the viewing Lambda on the view domain and the identity in the construct's Cognito pool (0069). Facts that shape the design:

- Cognito supports a public app client (no secret) with the authorization code grant and PKCE, `S256` only; the ID token carries `iss` = the pool's provider URL, `aud` = the client id and `token_use` = `id`, and the keys are at `<iss>/.well-known/jwks.json` ([App clients](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-client-apps.html); [Using PKCE](https://docs.aws.amazon.com/cognito/latest/developerguide/using-pkce-in-authorization-code.html); [Verifying JSON web tokens](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html)) (V8). The `nonce` sent to the authorize endpoint comes back in the ID token ([Authorize endpoint](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html)), and the pool's `ProviderURL` includes `https://` (F13).
- A cache behaviour that forwards no cookies makes CloudFront remove `Set-Cookie` from responses; one that forwards a named set passes `Set-Cookie` back ([Cache content based on cookies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Cookies.html); [Request and response behavior for custom origins](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html)). AWS does not say whether a `Set-Cookie` for a name outside that set passes too (F6). The owner chose a separate login behaviour forwarding one transaction cookie (Q2 A).

## Decision

- **Routes**, on the main host only (an artifact host gets 404), **GET only**: the login sub-app's first middleware answers every other method, HEAD included, with 405 `Allow: GET` before any cookie, key or `fetch` work, because Hono answers HEAD from GET handlers and a prefetched `HEAD /__artifact/callback` would spend the single-use code. Every response is `Cache-Control: no-store` with the security headers of 0025; error pages are HTML with `Content-Security-Policy: default-src 'none'`.
- **`/__artifact/login?return=`**: the return is validated (`validateReturn`: a string of at most 2048 characters without control characters, parsed with no base, `https:`, no userinfo or port, a host `DomainHostPolicy` accepts; else the gallery) and kept only if its JSON-escaped length is at most 1024 characters, else the gallery, which bounds the cookie. It reads the key set through the 5-minute cache (0079; 503 `login is unavailable` if it cannot), creates `state`, `nonce` and the PKCE verifier (32 random bytes each), sets the transaction cookie of 0078 **signed with the set's current `kid`**, and redirects to the authorize endpoint with `response_type=code`, `scope=openid email` and `code_challenge_method=S256`.
- **`/__artifact/callback`**, in order, with no session cookie on any failure: an `error` parameter → 400; the transaction cookie is verified through the key cache's `forKid` (an unknown `kid` forces one reload, at most once a minute, so a warm instance with the pre-rotation set does not answer "expired"), and missing, malformed, badly signed, unknown or expired → 400; `state` must equal the cookie's (constant time) → 400; `code` must match `[A-Za-z0-9._~-]{1,2048}` → 400; the token endpoint POST (form-encoded, 5 s timeout, a string `id_token` of at most 16 KB) failing → 502; the ID token must be three base64url segments with header `alg` `RS256` and a string `kid` whose JWKS key verifies the RSA-SHA256 signature (403; a JWKS fetch failure → 502), then `iss`, `aud` (string or array), `token_use` `id`, `sub`, `exp`/`iat` with 60 s skew, `nonce`, `email_verified` (`true` or `"true"`) and an `email` whose lowercase form is an owner → 403. On success it sets the session cookie (0078, signed with the current `kid`), clears the transaction cookie and redirects to the re-validated return.
- **JWKS:** fetched lazily, cached per warm instance for 24 hours as RSA signing keys only; an unknown `kid` refetches at most once per 60 seconds; fetches are single-flight and a failure caches nothing. Only `node:crypto` is used, so the runtime dependencies stay the v1 four.
- **`/__artifact/logout`:** clears the session cookie (same `Domain` and `Path`, `Max-Age=0`) and the transaction cookie, then redirects to the Cognito logout with `logout_uri` = the gallery, or straight to the gallery without a logout URL. A cross-site logout is accepted: cookie tossing from an artifact subdomain can already log a viewer out.
- **Logs:** `artifact login {"result":"ok"|"denied"|"error","reason":…,"status"?,"name"?}`, fixed fields only; never an email, code, token, cookie, `state` or `nonce`.
- **Login cache behaviour** (built with the distribution in a later commit): the three paths get their own behaviour with caching disabled and an origin request policy whose cookie allowlist is exactly `__Host-artifact_login`. This is a **deviation** from the plan's "no cookies forwarded", for these three paths and this one cookie only; the edge function still strips the session cookie there (0080). The `__Host-` prefix makes the browser refuse a version set by an artifact subdomain and requires `Path=/`, so the browser sends it on every path of the main host; the edge strips it everywhere but the login behaviour.
- **The F6 residual:** whether CloudFront passes the logout's `Set-Cookie` for `__Secure-artifact_session`, a name outside the allowlist, is checked after deploy by smoke check S40. If it fails, the owner stops and reports; the allowlist and policies are not changed, and the owner chooses between Q2's options B (a viewer-response function) and C.

## Consequences

Only an owner holding the IdP session can obtain a session cookie, and only for the browser that started the sign-in (PKCE, `state`, `nonce` and the host-only transaction cookie together). A long or hostile `return` costs the landing page, never a login loop or an open redirect. The verifier sits in the transaction cookie in plain text, which PKCE's threat model allows for an `HttpOnly`, `Secure`, host-only, 10-minute cookie. The issuer is configuration, so another OIDC provider with a JWKS would work without code changes. The session cookie is itself a name outside the allowlist, so if S40 shows that CloudFront drops such `Set-Cookie` headers, the callback cannot set it either and sign-in does not work until the owner decides.
