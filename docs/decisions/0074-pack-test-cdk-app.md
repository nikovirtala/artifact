# 0074. Pack test: optional peers, tarball CDK apps, CloudFormation Validate clean; CI without AWS

Status: Accepted (M9)

## Context

M9's criterion: a fresh `cdk init` app deploys `ArtifactHosting` from the tarball with under 20 lines of stack code, needing no esbuild, Docker or repo checkout. Deploying is the owner's check (`examples/personal/README.md`); offline, the pack test can prove everything up to synth. CDK runs CloudFormation Validate on every synth; with `@aws-cdk/core:validateAgainstDefaultRules: true`, which the `cdk init` template's recommended flags set, any finding fails the consumer's synth, and `@aws-cdk/core:strictCfnValidateErrors` also fails on warnings. The report goes to `cdk.out/validation-report.json` (upstream [`FEATURE_FLAGS.md`](https://github.com/aws/aws-cdk/blob/main/packages/aws-cdk-lib/cx-api/FEATURE_FLAGS.md) and `aws-cdk-lib` 2.273.0 `core/lib/private/synthesis-validation.js`; A20 in the M9 AWS facts).

## Decision

`scripts/pack-test.ts`, after the existing install and e2e run (and (a), 0073), synthesizes three apps outside the repo with every `AWS_*` variable removed, `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` pointing at nothing, `AWS_EC2_METADATA_DISABLED=true` and `CDK_DISABLE_CLI_TELEMETRY=true`:

- **(b) plain ESM.** `npm install <tarball> aws-cdk-lib@2.273.0 constructs@10.8.1` into a `"type": "module"` app; no `node_modules/esbuild`; an `app.mjs` of under 20 non-empty lines (placeholder account, a zone from `fromHostedZoneAttributes` for `example.dev`, `onDestroy: DESTROY`, `keepLast: 2`) synthesizes exactly two `index.handler` functions on `nodejs24.x`/arm64 whose code is a `cdk.out/asset.<hash>/` directory holding `index.mjs`. CDK's auto-delete provider is ignored.
- **(b2) other TypeScript consumers.** TypeScript 5.9.3 type-checks the same app as `app.ts` with `{"module":"commonjs","moduleResolution":"node10","target":"esnext"}` and with `{"module":"nodenext"}`, both `strict` and `noEmit`, then `node app.cjs` synthesizes through `require()` (Node 24's `require(esm)`). `target: "esnext"` is needed by `aws-cdk-lib`'s own declarations, not ours: under TypeScript 5's default target they fail with `TS18028` (private identifiers) and `TS2583` (`Map`/`Set`), and under `es2022` with `TS2304` (`Disposable`). **No `skipLibCheck`**: it would also skip `dist/cdk/*.d.ts` and turn an unresolvable specifier in our declarations into a silent `any`, which is what (b2) exists to catch.
- **(b3) the real `cdk init` app.** `npx aws-cdk@2.1145.0 init app --language typescript --generate-only`, then one `npm install <tarball> aws-cdk-lib@2.273.0 constructs@10.8.1` that also installs the template's own devDependencies. Not two installs: the template's `aws-cdk-lib: ^2.272.0` resolves to the newest release (2.274.0 from 2026-10-20, with `@aws-cdk/cloud-assembly-schema` 55), and npm 11's downgrade to 2.273.0 in a second install overrides the bundled `cloud-assembly-api`'s peer (ERESOLVE) and leaves `aws-cdk-lib/node_modules/@aws-cdk/cloud-assembly-schema` empty, marked `inBundle`, so synth fails with `Cannot find module`. The CloudShell guide installs the same way. The test first asserts the template facts it relies on (no `"type"` in `package.json`, `NodeNext` with `noEmit`, `"app": "npx tsc && npx tsx bin/init-app.ts"`), replaces `bin/init-app.ts` and `lib/init-app-stack.ts` with `scripts/lib/tarball-app.ts`'s `tarballAppFiles("init-app")` (zone id and name from context), runs `npx tsc` and `npx cdk synth -c zoneId=… -c zoneName=example.dev`, and asserts: `cdk.out/InitAppStack.template.json` with the same two functions; a bucket policy with only the two TLS denies and the auto-delete `Allow` (the template carries the 87 recommended flags); both `cdk.out/asset.*/index.mjs` byte-identical to the tarball's bundles; `validation-report.json` with `pluginReports: []`; and every `npm ls esbuild` path going through `tsx`, never through `@nikovirtala/artifact`.
- `tarballAppFiles(name)` produces the bin and stack files for a `cdk init` project name; for `tarball-app` it is exactly the code the CloudShell guide deploys, and an examples test compares the two.
- **CI** (`.github/workflows/ci.yml`): job-level `AWS_EC2_METADATA_DISABLED` and `CDK_DISABLE_CLI_TELEMETRY`; no credentials and no OIDC. `pnpm check` (unit, handler and construct tests, and from 0075 the `examples/personal` synth) and `pnpm test:pack` run on every pull request. `s3-contract.yml` and `publish.yml` are unchanged.

## Consequences

The pack test now needs the registry for the CDK, TypeScript 5.9.3, the `aws-cdk` CLI and the template's devDependencies, and takes about a minute longer. A change to the `cdk init` template, to our declarations, or to the construct's CloudFormation findings fails it before any consumer sees it. The construct needs no esbuild or Docker: it uses prebuilt `Code.fromAsset` directories with no bundling; esbuild in a `cdk init` app comes from `tsx`.
